# Artifact Handling Strategy: Lazy Loading via Paths

## Summary

This document outlines the strategy for handling large artifacts (e.g., images, data files) generated by ATHOS flows. To ensure efficiency and scalability, flows **must** use a lazy-loading pattern by saving artifacts to the session workspace and returning a path reference, rather than embedding large data payloads directly into `FlowOutput` objects.

## Problem

The `Artifact` model contains a `data: Optional[Any]` field, which could tempt developers to load large files into memory. This approach leads to:
- **High Memory Consumption:** Loading large files into memory is inefficient and can lead to performance degradation, especially under concurrent loads.
- **Slow Response Times:** The system must read the entire file from disk and serialize it before returning a response.
- **Inflexibility:** The receiving application (e.g., OpenWebUI) is forced to handle a large data payload, when it might only need to provide a download link.

## Solution: Path-Based Lazy Loading

The `Artifact` model also contains a `path: Optional[str]` field. This is the designated mechanism for handling artifacts.

### Required Development Work

To make this pattern robust and secure, the following work is required:

1.  **Workspace File Server:**
    - An HTTP endpoint must be added to the `athos-pipeline` server (or a sidecar service).
    - This endpoint (e.g., `/files/`) will be responsible for securely serving files from the ATHOS workspace directory (e.g., `/app/workspace`).
    - It must handle security considerations, such as ensuring that users can only access files within their own session directories.

2.  **URL Transformation in Integrations:**
    - Integrations, such as the OpenWebUI `Pipeline` class, must be updated to transform the internal filesystem paths into publicly accessible URLs.
    - **Example:** A path like `/app/workspace/user-abc/session-123/plot.png` must be converted to `http://<server_address>/files/user-abc/session-123/plot.png` before being sent to the frontend.

3.  **Artifact Cleanup Strategy:**
    - A mechanism for cleaning up stale artifacts must be implemented to prevent disk space exhaustion.
    - This logic should be tied to the session lifecycle. When a session is deleted via `SessionStore.delete()`, the corresponding workspace directory and all its contents on the filesystem should also be removed.

4.  **Developer Documentation & Convention:**
    - The official developer documentation must be updated to clearly state that large artifacts **must** be handled via the `path` attribute.
    - The convention should be:
        1.  Generate the artifact data.
        2.  Save the data to a file within the directory provided by `input.session.workspace`.
        3.  Create an `Artifact` object with the `path` field set to the file's path.
        4.  The `data` field should be left as `None`.

By implementing this infrastructure, we make the lazy-loading pattern the standard, ensuring the ATHOS platform remains performant and scalable.
