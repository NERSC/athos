# nersc-athos

ATHOS: Agentic Toolkit for HPC Operations Support

## Dev setup

Requirements:

- Python 3.10+

Local development:

```bash
pip install -e .[dev]
```

On NERSC systems, simply run the provided setup script:

```bash
./scripts/create_env_nersc.sh
```

### Environment configuration

Depending on the tools you plan to configure, you will need to set specific
environment variables for ServiceNow, SFAPI, Iris, or CBORG integrations. The
provided `.env.template` is a convenience reference showing which variables are
available to configure; you can also copy it locally and edit the values to suit
your environment:

```bash
cp .env.template .env
```

Update the copied file with your ServiceNow credentials, NERSC client
certificate details, and optional Iris or CBORG settings. The template enables
the default shared workspace path (`${SCRATCH}/athos/workspace`) and leaves the
remaining settings commented out so they can be customized as needed.

## Shared Workspace

ATHOS tools and MCP servers can share a common workspace directory so that
files generated by one component are immediately visible to others. Configure
this directory by setting the `ATHOS_WORKSPACE` environment variable or by
editing `workspace_dir` in `config/config.yaml`. The filesystem MCP server
will be granted write access to this directory, so choose a path with
appropriate permissions. Helpers for inspecting or clearing the workspace are
available in `athos.utils.workspace`.

## Running the command line interface

On NERSC you must first load Conda and activate the ATHOS environment in each session:

```bash
ml conda
conda activate athos
```

From the top level folder, you can run the CLI using the `athos` command:

```bash
athos --config config/config.yaml --flow lang_chat --input "what is NERSC?"
```

You can override the configured logging verbosity for a single run using
`--log-level`:

```bash
athos --config config/config.yaml --flow lang_chat --input "what is NERSC?" --log-level DEBUG
```

To tweak configuration values without editing the YAML file, use one or more
`--set` overrides with dot notation:

```bash
athos --config config/config.yaml --flow lang_chat --input "hi" \
  --set models.gpt_4o.temperature=0.5 --set models.gpt_4o.max_tokens=50
```

Values are parsed as YAML, so wrap strings in quotes. Nested keys are
separated by dots.

To launch a simple Gradio interface for a flow instead of running a single
query, pass the `--gradio` flag (optionally selecting a port with `--port`):

```bash
athos --config config/config.yaml --flow lang_chat --gradio --port 7860
```

To view a summary of the loaded configuration and exit without running a
flow, use:

```bash
athos --config config/config.yaml --show-config
```

### Storing prompts alongside your configuration

Large system prompts or agent instructions can be stored in external files to
keep `config/config.yaml` concise. Provide a `system_prompt_path` or
`instructions_path` field anywhere a `system_prompt` or `instructions` string is
accepted (for example under `models` or within individual flow definitions).

- Paths are resolved **relative to the YAML file** being loaded, so a prompt in
  `config/prompts/example.md` can be referenced with
  `system_prompt_path: "prompts/example.md"`.
- The loader reads each referenced file as UTF-8 text and automatically
  populates the corresponding inline field. Explicit string values in the YAML
  continue to work and take precedence when no path is supplied.
- Environment variables may be embedded in the path using the existing
  `${VAR}`/`${VAR:-default}` syntax and are expanded before resolution.
- The `_path` entries are consumed during loading, so the resulting
  configuration objects only expose the populated `system_prompt`/`instructions`
  strings.

This project ships with sample prompts in `config/prompts/` that demonstrate the
convention.

### Logging

Logging behavior is controlled through the optional `logging_config` section in
your YAML configuration. Simple dictionaries with `level` and `format` keys are
passed through to `logging.basicConfig`. If you provide a `version` key, the
dictionary is treated as a full `logging.config.dictConfig` specification.
For convenience a lightweight schema is also supported:

```yaml
logging_config:
  level: INFO
  format: "%(asctime)s %(levelname)s %(message)s"
  handlers:
    - type: console
    - type: file
      filename: /tmp/athos.log
```

When `handlers` are present the helper converts the dictionary into a `dictConfig`
and configures the root logger accordingly. If a file handler specifies a path
whose parent directory doesn't exist, it will be created automatically.

## Package Structure

The project is structured as a single Python package `athos` with the following modules:

### `src/athos/interfaces/`
**Shared flow interfaces**

Provides the foundational `BaseFlow` protocol that concrete implementations extend.

### `src/athos/registry/`
**Flow registration utilities**

Hosts the flow registry and helper functions that extensions use to advertise
new flow types.

### `src/athos/runtime/`
**Runtime builders**

Contains helpers such as `build_config`, `build_flow`, and `create_flows` that
assemble flows from configuration files.

### `src/athos/frameworks/smolagents/`
**SmolAgents-backed implementation**

SmolAgents is the default framework shipped with Athos. This package contains
the concrete flow implementations and supporting factories:

- **`factories.py`**: Utility functions for building models, tools, and MCP clients
- **`flows/agent.py`** and **`flows/chatbot.py`**: Built-in SmolAgents flows registered with the core registry

### `src/athos/frameworks/langgraph/`
**LangGraph-backed implementation**

LangGraph-based flows and helpers for authoring graph-style agent workflows.



### `src/athos/tools/`
**HPC-specific tools and utilities**

Custom tools designed for HPC operations:

- **`slurm_query.py`**: Utility for querying SLURM jobs
- **`slurm_mcp/`**: MCP server providing secure SLURM command execution
- **`servicenow_mcp/`**: Tools for interacting with ServiceNow from HPC workflows
- **`sfapi_mcp/`**: MCP server for NERSC SFAPI integrations
- **`rag_mcp/`**: MCP server for RAG workflows
- **`chroma/`**: ChromaDB helpers for RAG storage

### `src/athos/examples/`
**Usage examples and demonstrations**

Example scripts demonstrating agent and tool integrations can be found in this
directory. For instance, `filesystem_agent.py` showcases the MCP filesystem
tools, and `servicenow_agent.py` demonstrates interacting with a ServiceNow
instance through the ServiceNow MCP server. You can choose which ServiceNow
tasks to run using `--tasks` and specify an incident with `--incident`.

### `examples/`
**Top-level examples and walkthroughs**

Additional examples live in the top-level `examples/` directory. See
`examples/README.md` for runnable walkthroughs and setup notes.

### `src/athos/integrations/`
**Integration adapters**

Integration-specific modules (e.g., ServiceNow, Slackbot) live here.

### `src/athos/main.py`
**CLI interface and entry point**

Main command-line interface for running ATHOS agents with configuration-driven execution.

### `evals/`
**Test cases and evaluation pipeline**

Synthetic use cases to evaluate performance of agent configurations.
See [evals/README.md](evals/README.md) for instructions on how to run.

## MCP servers and entry points

The following console entry points are installed with the package:

- `athos`: main CLI
- `servicenow-mcp`: ServiceNow MCP server
- `nersc-sfapi-mcp`: SFAPI MCP server
- `rag-mcp`: RAG MCP server

## Key Architecture Notes

- The project uses a **configuration-driven approach** where models, tools and flows are defined in YAML configuration files
- **Registry-based architecture** enables dynamic loading of flow implementations when their modules are imported
- **Multiple flow types** are supported (chatbot, code agent, prompt chains)
- The framework supports **Hugging Face SmolAgents** and **LangGraph** flows, and can be extended with other agent frameworks

### Extending Tools and Flows

To provide additional flows, ensure your package imports a module that calls the
`athos.registry.flow_registry.register_flow` helper. Importing that module from your
application will make the new functionality available without relying on
packaging entry points.

Tools are instantiated directly from configuration using the
`athos.frameworks.smolagents.factories.build_tool` helper, which loads the module and callable defined
in `ToolConfig`. Supplying the correct module path and callable name is
all that is required to extend the available tooling.
